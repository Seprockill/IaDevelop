- (capability by spec) CAP-3: Heterogeneous Hardware Placement. System inspects pod resource specifications and routes workloads automatically to the optimal node tier based on VRAM capacity (24 GB Standard vs 2x48 GB High-Capacity).
- (capability by spec) CAP-4: Distributed Training Workload Lifecycle. Researchers can launch, monitor, checkpoint, and resume multi-GPU and multi-node Kubeflow training jobs with elastic preemption tolerance.
- (capability by spec) CAP-5: Cluster Telemetry & Node Eviction. System continuously ingests real-time hardware telemetry (VRAM usage, compute utilization, thermal, power) and automatically cordons and drains nodes violating health thresholds.
- (capability by spec) CAP-6: Role-Based Access Governance. Platform enforces role-based permissions (Administrator, Instructor, Student, Lab Operator, Privileged Researcher) linked to institutional identity providers for resource discovery and operation execution.

Software slicing introduces memory overlap risks and unpredictable degradation; strict isolation prevents single OOM errors from cascading and crashing entire shared nodes during intensive classification/training workloads.
- (justification by student) Rejection: Public cloud bursting (AWS/GCP). Core institutional mandate is maximizing utilization and ROI of existing on-premise fleet. Cloud bursting introduces unbounded, unpredictable billing risks unabsorbable by academic budgets, along with data residency and privacy risks for sensitive institutional research.
